Domain 1: Solution Design & Architecture 17%

1.1 · Translate business problems into Claude-based AI solutions

Rule: If a part of the problem is exact (a lookup, a rule, a sum), give it to code; if it is language or judgement, give it to Claude, and stop at the simplest design that meets every stated constraint.
When the stem says…PickWhy
Part of the task is an exact lookup or calculationPlain code, a query or a toolExact, cheap and testable, with no model guesswork
The task is reading messy text and making a judgementA Claude call with a clear promptThis is where a language model adds value
The answer depends on private or changing documentsClaude plus retrieval (an augmented LLM)The model needs the facts at request time
The decision is high-impact or regulatedClaude drafts, a person approvesKeeps accountability with a person
The steps cannot be known in advanceAn agentOnly then does the extra autonomy pay for itself

1.2 · Design end-to-end architectures (input → processing → output → feedback loops)

Rule: If quality drifts unseen, add the feedback loop; if bad data gets in, validate input; if bad formats get out, validate output in code.
When the stem says…PickWhy
Quality drifted after launch and nobody noticedAdd the feedback loop and monitoringNothing was measuring quality in production
Blank or unsupported files cause invented answersValidate at the input stageCheaper to reject early than to repair later
A downstream system breaks on bad formatsValidate output against a schema in codeCatches errors before delivery
Users fix outputs by hand every dayCapture the corrections as labelled dataTurns daily work into eval cases
One known case fails because the prompt is plainly wrongFix the prompt, then add the case to the evalsA direct defect is fixed directly; the loop stops it coming back

1.3 · Select appropriate architectural patterns (workflow, agentic, augmented LLM)

Rule: Pick the least autonomy that solves the problem: one answer from documents gets an augmented LLM, fixed steps get a workflow, and open-ended work gets an agent.
When the stem says…PickWhy
One question, answered from documentsAugmented LLM with retrievalThere is no sequence of steps to manage
Every item goes through the same known stepsWorkflow: prompt chainingA fixed order is predictable and testable
Inputs fall into distinct types that need different handlingWorkflow: routingEach type gets its own tuned prompt or model
A draft must meet clear criteria, and critique helpsWorkflow: evaluator-optimizerRepeated refinement against a checkable standard
The next step depends on what was just foundAgentOnly a model-directed loop can change the path as it goes

1.4 · Design multi-agent systems and orchestration strategies

Rule: If the work splits into independent or specialist parts, use a coordinator with scoped subagents and full briefs; if the steps depend on each other, keep one agent with good tools.
When the stem says…PickWhy
One user goal, a handful of tools, steps that depend on each otherA single agentCoordination would add cost with no gain
Many independent research threadsCoordinator with parallel subagentsBreadth runs in parallel, in separate contexts
One part needs permissions the others must not haveA separate specialist subagentIsolates tools and access by role
Subagents return inconsistent or repetitive resultsFuller briefs plus a coordinator checkSubagents know only what they are told

Study and practise 1.4 →

1.5 · Apply decomposition techniques for complex problem solving

Rule: If the steps are known, chain focused prompts with a check between each; if one input is too big to review well, do per-item passes and then an integration pass; if the steps depend on findings, decompose adaptively.
When the stem says…PickWhy
One prompt does extraction, analysis and writing, and quality is unevenA prompt chain with checks between stepsEach step gets full attention and can be tested
Reviewing a forty-file change misses issuesPer-file passes, then an integration passDepth on each file plus a cross-file view
The plan depends on what the first findings showAdaptive decompositionA fixed chain cannot follow new leads
A simple task is already done well by one promptKeep the single promptExtra steps would only add latency and cost

1.6 · Align solutions to business value pillars (efficiency, transformation, productivity, cost, performance SLAs)

Rule: If the sponsor wants lower cost, pick the cheapest design that meets the quality floor; if they want an SLA, design for the latency target; if they want something new, judge it by adoption; and always measure that pillar against a baseline.
When the stem says…PickWhy
The goal is a lower cost per ticketThe cheapest configuration that meets the quality floorServes the cost pillar directly
Answers must arrive within an agreed timeA fast model and streaming on the live pathMeets the performance SLA
The goal is a service customers could not get beforeA more capable design, judged by adoption and revenueTransformation can justify a higher cost
Analysts want to handle more cases each dayAssisted drafting, with a person finishingProductivity: more output per person

Domain 2: Claude Models, Prompting & Context Engineering 13%

2.1 · Select appropriate Claude models based on trade-offs

Rule: If a smaller model passes your eval, use it; if only some requests are hard, route just those to a capable model; if nobody is waiting for the answer, batch it.
When the stem says…PickWhy
Millions of simple, well-defined items a dayA smaller, faster model validated on an evalMeets quality at a fraction of the cost
Hard multi-step reasoning or complex agent workThe most capable modelSmaller models fail the quality bar here
Traffic is a mix of easy and hard requestsRoute by difficultyCheap for most requests, capable where needed
Results are needed by tomorrow, not instantlyBatch processingLower price, and latency does not matter
The small model fails the eval on important edge casesMove up a tier, or route only those cases upThe quality bar comes before cost

2.2 · Design system prompts, templates, and guardrails

Output must always be valid JSON for a parserValidate against a schema in codeA request in the prompt can still fail

A rule must never be broken, such as a refund limitEnforce it in the tool, not just the promptCode is deterministic; prompts are not

2.3 · Apply prompt engineering techniques (zero-shot, few-shot, chain-of-thought)

Rule: If the task is clear and passes, stay zero-shot; if format or borderline cases wobble, add varied examples; if the format is right but the logic is wrong, let Claude reason before it answers.
When the stem says…PickWhy
A clear, simple task that already passesZero-shotAny extra technique adds cost without benefit

A quick lookup with a tight latency budgetNo chain-of-thoughtReasoning would add delay for no gain

2.4 · Optimize context windows and manage token usage

Rule: If context grows with history, summarise old turns and pin exact facts; if tools return bulk, trim it at the source; if documents are large, retrieve the relevant parts, and put any long document first and the question last.
When the stem says…PickWhy
Cost rises with conversation length because the full history is resentSummarise old turns and pin key factsSmaller context, with exact values kept
A tool returns 200 fields and the task uses fiveTrim tool output to the needed fieldsLess noise and fewer tokens on every call
The whole policy library is pasted into every promptRetrieve the relevant sectionsSends only what the question needs
A short, stable reference text is needed on every requestKeep it in context and cache itRetrieval would add a step for no saving
Answers miss a detail in a long documentDocument first, question lastHelps the model use long inputs

2.5 · Implement prompt reuse strategies (caching, modular prompts, Skills)

Rule: If the same long content goes with every request, put it first and cache it; if many prompts share rules, build them from modules; if expertise is needed only sometimes, package it as a Skill.
When the stem says…PickWhy
The same long system prompt and policy go with every request; cost and latency matterStatic content first, then prompt cachingThe repeated prefix is read from the cache

Many specialist procedures, each needed only now and thenAgent SkillsLoaded on demand, not on every request
Each request is one-off, or its start changes every timeNo cachingNothing repeats, so the cache would not be reused

Domain 3: Integration 19%

3.1 · Evaluate tool/agent configuration for capability bloat

Rule: If the role never uses a capability, remove it from both the tool list and the account; if it is rarely used but high-impact, keep it behind human approval.
When the stem says…PickWhy
The role never uses a tool the agent hasRemove the toolEliminates the risk entirely
The role needs the tool, but rarely, and the action is high-impactKeep it behind human approvalRemoving it would block real work
The role needs a tool, but only part of itReplace with a narrower toolKeeps the job possible with less power
The agent runs under a shared or admin accountGive it its own scoped identityThe permission layer is the backstop if a tool slips through
Auditors need a record of what happenedAdd logging as wellLogging supports, it never replaces, least privilege

3.2 · Analyze authentication and authorization requirements to identify security gaps

Rule: If users can reach data they could not open themselves, act with their delegated, scoped token and filter retrieval by their access; if users are not signed in at all, fix authentication first.
When the stem says…PickWhy
The agent acts for individual users in systems that already have per-user permissionsDelegated, user-scoped tokenThe system enforces what that user may do
Users see answers from documents they could not open themselvesFilter retrieval by each chunk's access listRestricted text never reaches the model
Access rules are coarse and match teams cleanly (say, one index per legal entity)Separate indexes per groupSimpler, and enough when permissions follow the split
A background job with no user behind it (nightly batch)Its own narrowly scoped service identityThere is no user to delegate from, so least privilege applies to the service
Users are not signed in at allFix authentication firstAuthorization needs a known identity to work from

3.3 · Evaluate accuracy-latency trade-offs and justify configuration decisions

Rule: If the SLA is tight and only some requests are hard, route those to the heavy path; if a check's result is used later, move it off the live path.
When the stem says…PickWhy
Most requests are easy, a few are hard, and the SLA is tightRoute: fast path by default, heavy path for hard casesKeeps p95 low and accuracy where it matters
A check improves accuracy but the result is used laterVerify asynchronously, off the live pathAccuracy gain without user-facing delay
A person reads a long answer and complains it feels slowStream the outputPerceived speed improves; nothing else changes
Every request is high-stakes and the SLA is looseThe heavier, more accurate configuration everywhereLatency has room, so take the accuracy
A long, identical prefix is sent on every callPrompt cachingLower time to first token at no accuracy cost

3.4 · Analyze observability challenges and select monitoring strategies at scale

Rule: If you can't tell which step failed, trace every request under one ID; if spend or slowness hides in totals, measure per request and per step with percentiles; if quality may drift, score a live sample.
When the stem says…PickWhy
Can't tell which step in a multi-step system caused a bad answerEnd-to-end tracing with one request IDShows each step's input and output in context
Spend rose but volume didn't, or some users are very slowPer-request, per-step token, cost and latency percentilesFinds the expensive or slow path that totals and averages hide
Quality may be drifting, but nothing errorsSampled quality evals with alertsQuality is invisible to system metrics
The failing step is already known and needs detailRicher logging on that stepTargeted detail is cheaper than logging everything

3.5 · Design a RAG pipeline with appropriate chunking and indexing strategies

When the stem says…PickWhy
A clause or table is split across two chunksStructure-aware chunking with overlapKeeps each idea in one retrievable piece

3.6 · Apply retrieval strategies matched to data shape and query pattern

When the stem says…PickWhy

Rule: If you cannot say what “good” is as a number, define the metric and target before changing anything; if a stem mentions perceived speed, think time to first token, and if it mentions outside content, add a security metric.
When the stem says…PickWhy

A nightly job nobody waits onThroughput and cost per taskFirst-token speed does not matter when no one is watching

Open-ended answers with many good wordingsRubric score from a judge or a personExact match would mark good paraphrases wrong

Domain 5: Governance, Safety & Risk Management 14%

5.1 · Implement guardrails and safety controls

Rule: If a rule must always hold, enforce it in code or permissions; if it is a soft preference, guide it in the prompt; and assume untrusted content will sometimes inject, so limit what the tools can do.
When the stem says…PickWhy
A rule that must always hold (a refund ceiling, approved recipients)Enforce it in tool code or permissionsDeterministic; a prompt is followed most of the time, not always
Untrusted content reaches the model (web pages, emails, uploads)Treat it as data and limit what the tools can doSome injection will get through, so limit the damage it can cause
A tone, style or scope preference that does little harm if missedGuide it in the system promptHere the prompt wins: code enforcement would be heavy for a soft rule
Sensitive data must never appear in responsesKeep it out of the context, and redact output as a backstopData the model never sees cannot leak
