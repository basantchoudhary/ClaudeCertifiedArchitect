3.1 · Evaluate tool/agent configuration for capability bloat

Guide line: “Evaluate tool/agent configuration for capability bloat”

In one sentence: Give an agent only the tools and permissions its job needs, because every extra one is a risk and a distraction.

Capability bloat means an agent has been given more tools, permissions or data access than its role uses. It usually happens by accident: a team connects a whole MCP server or reuses an admin account because it is quicker.

Each extra capability is attack surface: something a prompt injection, a confused model or a misuse could trigger. It also makes the model's job harder, because more tools means more chances to pick the wrong one.

The fix is least privilege: list what the role actually does, and remove everything else. Removing a capability eliminates the risk; logging it or asking for confirmation only reduces or reveals it. Apply it in two places: the tool list the agent sees, and the identity (account or token) the tools run under, so that even a tool that slips through cannot do more than the role allows.

List the role's tasks→Map tasks to tools→Remove the rest→Scope permissions per tool→Review when the role changes

Know this

  • Least privilege: an agent gets the minimum tools and permissions its role needs.
  • Removing a capability is a preventive control; logging and confirmation prompts are detective or compensating controls.
  • Read-only and write tools should be separate, so a read-only role never holds write access.
  • Fewer, well-described tools also improve tool selection.
  • Restrict both the tools the agent can see and the permissions of the account those tools use.
  • A bigger or better model does not change what the agent is authorised to do.

Worked example

Situation: An internal HR assistant was connected to the full HR MCP server, which can read, edit and delete employee records. Staff only ask it policy questions and look up their own leave balance.

Decision: Give it a read-only policy search tool and a leave-balance tool scoped to the signed-in employee. Remove edit and delete entirely.

Why: Nothing in the role needs write access, so removing it closes the risk. Approval prompts on edits would still leave the capability one injected instruction away.

Rule to remember: If the role never uses a capability, remove it from both the tool list and the account; if it is rarely used but high-impact, keep it behind human approval.

3.2 · Analyze authentication and authorization requirements to identify security gaps

Guide line: “Analyze authentication and authorization requirements to identify security gaps”

In one sentence: Know who is asking, then let the agent reach only what that person is allowed to reach, enforced in the data layer rather than the prompt.

Authentication answers “who is this?”: the user signs in, or a service proves its identity with a token. Authorization answers “what may they see or do?”: the permissions attached to that identity. Most agent security gaps are authorization gaps: everyone is properly signed in, but the agent reaches data on their behalf with far more access than they have.

The classic gap is the shared service account: the agent calls every system with one powerful identity and decides in its own logic, or in the prompt, whose data to fetch. Any user can then get any data by asking cleverly. This is a confused deputy: a trusted component tricked into using its own authority for someone who lacks it. The fix is delegated access: the agent acts with a token issued for the signed-in user (for example through OAuth), scoped to what that user may do, so the target system enforces the user's own permissions. Remote MCP servers follow the same idea; the MCP specification uses OAuth-based authorization for servers reached over HTTP.

Retrieval needs the same care. If a RAG index is built from documents with different access rules, store each chunk's access-control list (who may read it) as metadata and filter by the user's identity at retrieval time, so restricted text never reaches the model. A system-prompt rule or an output filter applied afterwards is too late: the data has already been read. Finally, keep secrets out of prompts, and log both the user and the agent on every action so audits can tell them apart.

User signs in→Agent gets a user-scoped token→Tool or data layer checks permissions→Retrieval filters by the user's access→Audit log records user and agent

Know this

  • Authentication proves identity; authorization decides access. Signing in users does not fix an authorization gap.
  • An agent using one shared, all-powerful account lets any user reach any data: act with the user's delegated, scoped token instead.
  • Enforce access in the tool or data layer; a prompt instruction is not an access control.
  • Permission-aware retrieval filters chunks by the user's access list before they reach the model.
  • Remote MCP servers use OAuth-based authorization, so tool calls can carry the user's own scoped access.
  • Credentials belong in a secrets store or environment, never in prompts or tool descriptions.
  • Audit logs should record which user and which agent performed each action.

Worked example

Situation: An internal assistant answers questions from an index built over the whole company document store, using a crawler account that can read everything. A salesperson asked about bonuses and got figures from an HR compensation file.

Decision: Index each document's access list with its chunks, and filter every search by the signed-in user's groups. Tools that fetch full documents call the store with the user's delegated token.

Why: The gap is authorization, not authentication: the salesperson was properly signed in. A prompt rule like “don't reveal salaries” would still let the model read the file and depends on the model obeying; filtering at retrieval stops the text from ever arriving.

Rule to remember: If users can reach data they could not open themselves, act with their delegated, scoped token and filter retrieval by their access; if users are not signed in at all, fix authentication first.

3.3 · Evaluate accuracy-latency trade-offs and justify configuration decisions

Guide line: “Evaluate accuracy-latency trade-offs and justify configuration decisions”

In one sentence: Most things that make answers better also make them slower, so pick the configuration that meets the latency target with acceptable accuracy, and prove it with numbers.

A latency SLA (service-level agreement) is a promise such as “95% of replies start within one second”. The p95 is the time 95% of requests beat; it matters more than the average because the slow tail is what users notice. Two timings matter: time to first token (when output starts) and total time (when it finishes).

Almost every accuracy lever costs time: a larger model, extended thinking, retrieving more chunks, a reranker (a second model that re-scores retrieved results), a verification pass, or more agents. Speed levers include a smaller, faster model, prompt caching, running independent calls in parallel, and doing work in advance.

The architect's moves are: route so only hard or high-stakes requests take the slow, accurate path; move checks off the live path (verify asynchronously when the result is not needed instantly); and stream output so a person sees text sooner. Streaming only improves perceived speed for a human reader; it does not help when a program needs the complete result or when the slow part happens before the first word. Justify the choice with a table of accuracy and p95 latency for each candidate configuration on the eval set.

Measure accuracy and p95 per configuration→Compare with the SLA→Route hard cases to the heavy path→Move checks off the live path→Re-measure

Know this

  • Larger models, extended thinking, reranking, more retrieval and verification passes raise accuracy and latency together.
  • Judge latency by percentiles (p95, p99) and time to first token, not the average.
  • Routing sends only hard or high-risk requests to the slower path, so most traffic stays fast.
  • Asynchronous verification fits when the checked result is used later, not in the live reply.
  • Streaming improves perceived speed for human readers only; it does not shorten total time.
  • Prompt caching cuts time to first token when a long prefix repeats.
  • Justify a configuration with measured accuracy and latency from the eval, not intuition.

Worked example

Situation: A bank's internal search assistant must answer within two seconds at p95. Adding a reranker raises answer accuracy from 81% to 90% on the eval but pushes p95 to 3.4 seconds. Accuracy matters most on regulatory questions, which are about 10% of traffic.

Decision: Use the reranker only for questions classified as regulatory; keep the fast path for the rest. Report accuracy and p95 for both paths.

Why: Routing keeps overall p95 inside the SLA while getting the accuracy gain where it counts. Turning the reranker on everywhere breaks the SLA; dropping it everywhere gives up accuracy on the questions that need it.

Rule to remember: If the SLA is tight and only some requests are hard, route those to the heavy path; if a check's result is used later, move it off the live path.

3.4 · Analyze observability challenges and select monitoring strategies at scale

Guide line: “Analyze observability challenges and select monitoring strategies at scale”

In one sentence: When an answer is wrong, you must be able to see every model call, tool call and retrieval that produced it, and you need numbers, not log reading, at scale.

Observability means being able to tell what a system did and why from the data it records. LLM systems make this hard: the same input can give different outputs, one answer may come from many steps (several model calls, tool calls, retrievals, sometimes several agents), and “wrong” is often a quality judgement rather than an error code.

The backbone is end-to-end tracing: one request ID carried through every step, with each step recorded as a span (a timed record of one operation: its inputs, outputs, model, tokens and duration). Open standards such as OpenTelemetry are commonly used. With a trace you can open one bad answer and see which retrieval returned the wrong chunk or which tool returned an error.

On top of traces, track metrics per request and per step: input and output tokens and cost, latency percentiles (p50, p95, p99, because averages hide the slow tail), tool error rates, and the prompt and model version used. Quality cannot be read from metrics, so run sampled quality evals: score a random slice of live traffic with automated checks or an LLM judge, and alert when scores drop. Handle personal data in logs deliberately (redact or restrict access).

Request ID assigned→Spans for each model, tool and retrieval step→Tokens, cost, latency per span→Sampled quality scoring→Dashboards and alerts

Know this

  • One request ID across every agent, model call, tool call and retrieval lets you find the failing step.
  • Record tokens and cost per request and per step; daily totals cannot show which feature or step is expensive.
  • Use latency percentiles (p95, p99); averages hide slow outliers.
  • Quality needs its own signal: sampled evals on live traffic, with alerts on drops.
  • Log the prompt version and model version with each request so regressions trace to a change.
  • Raising log verbosity without correlation gives more text, not more insight.
  • Prompts and responses can contain personal data: redact or restrict access to logs.

Worked example

Situation: A support platform runs a router, a retrieval step and two specialist agents. Customer satisfaction is falling, yet error rates and average latency look normal.

Decision: Add tracing with one request ID across all steps, record tokens, cost and p95 latency per step, and score a daily sample of conversations with an LLM judge calibrated on human ratings.

Why: Nothing is erroring, so system metrics alone won't show the cause; sampled evals reveal the quality drop and traces show which step is responsible. More verbose per-service logs would still leave engineers stitching steps together by hand.

Rule to remember: If you can't tell which step failed, trace every request under one ID; if spend or slowness hides in totals, measure per request and per step with percentiles; if quality may drift, score a live sample.

3.5 · Design a RAG pipeline with appropriate chunking and indexing strategies

Guide line: “Design a RAG pipeline with appropriate chunking and indexing strategies”

In one sentence: Cut documents into pieces that each make sense on their own, label them with useful metadata, and keep the index in step with the source.

RAG (retrieval-augmented generation) finds relevant passages and gives them to the model with the question. Before retrieval can work, documents are split into chunks, each turned into an embedding (a list of numbers that captures meaning) and stored in an index. How you chunk decides what can be found: a chunk that cuts a clause in half can never be retrieved whole.

Fixed-size chunking (every 500 characters) is simple but ignores meaning. Structure-aware chunking splits on the document's own boundaries: headings, sections, clauses, list items, table rows kept together. A little overlap between neighbouring chunks protects ideas that cross a boundary. Chunk size is a trade-off: small chunks match precisely but lack context; large chunks carry context but dilute the match. A common pattern retrieves small chunks and then passes their larger parent section to the model.

Chunks often lose the context that made them meaningful (“the limit is 25 days” without saying which country). Two fixes. Attach metadata (source, section, date, version, region, access list) for filtering and citation. Use contextual retrieval, a technique Anthropic has described: before indexing, prepend each chunk with a short, model-written note situating it in its document, and index that for both embedding and keyword search. Finally, re-index when documents change: update changed files, delete removed ones, and embed queries with the same embedding model as the index.

Parse by structure→Chunk with overlap→Add context and metadata→Embed and index→Re-index on change

Know this

  • Structure-aware chunking (by section, clause or heading) beats fixed-size chunking for structured documents.
  • Overlap between chunks protects ideas that cross a boundary.
  • Small chunks match precisely but lack context; large chunks carry context but match loosely.
  • Metadata such as source, date, version, region and access list enables filtering and citations.
  • Contextual retrieval prepends a short document-aware summary to each chunk before embedding and keyword indexing.
  • Re-index when sources change, remove deleted documents, and use the same embedding model for queries and index.
  • Tables should stay whole, or be stored as structured data, rather than split mid-row.

Worked example

Situation: A manufacturer's maintenance assistant indexes equipment manuals in fixed 1,000-character chunks. Technicians get half a procedure: step 4 onwards sits in a different chunk from steps 1 to 3, and warnings tables are split mid-row.

Decision: Re-chunk by heading and procedure, keep each procedure and each table whole, add modest overlap, and tag chunks with machine model and manual version.

Why: The failure is in how text was cut, so the fix is in chunking. Raising top-k might fetch both halves by luck but also floods the context with unrelated text; a bigger model cannot reason over steps it never received.

Rule to remember: If ideas are split across chunks, chunk by the document's structure with overlap; if chunks lose their context, add metadata and contextual notes; if sources change, re-index.

3.6 · Apply retrieval strategies matched to data shape and query pattern

Guide line: “Apply retrieval strategies matched to data shape and query pattern”

In one sentence: Choose how to search by what the data looks like and how people ask: meaning, exact terms, filters, or a real query against structured data.

Semantic (vector) search compares embeddings, so it finds passages with similar meaning even when the words differ. It is weak on exact strings: product codes, error codes, part numbers and names can look alike in meaning space. Keyword search, usually with the BM25 ranking method, scores documents by matching the exact terms, so it excels at codes and names but misses paraphrases.

Hybrid search runs both and merges the results, which suits collections where users mix exact identifiers with descriptions. Metadata filters (date, region, product version, owner) narrow the search before or during ranking. A reranker takes the top few dozen candidates and re-scores them with a more precise model, lifting the right passage from position 30 into the top 5 at some cost in latency.

Some data should not be embedded at all. Questions about totals, counts, trends or filters over tables (“revenue by region last quarter”) need exact computation over every row, so give the model a query tool over the database or warehouse, ideally one with defined metrics, and let it answer from the result. Retrieving the 20 most “similar” rows cannot add up two million.

Know this

  • Vector search matches meaning; it is weak on exact identifiers such as codes, SKUs and names.
  • BM25 keyword search matches exact terms; it misses paraphrases and synonyms.
  • Hybrid search combines both for collections where users mix codes with descriptions.
  • Metadata filters handle date, region, version and owner constraints precisely.
  • A reranker improves precision when the right result is retrieved but ranked too low.
  • Aggregations and exact figures over structured data need a query tool, not embeddings.
  • A better embedding model still matches by meaning, so it does not fix exact-match failures.

Worked example

Situation: A retailer's merchandising assistant answers both “What do customers say about the waterproof jackets?” and “How many units of SKU 88213 sold in Germany in March?” from one vector index of reviews and sales rows.

Decision: Keep semantic search over reviews; route sales questions to a tool that queries the sales warehouse with filters for SKU, country and month.

Why: Reviews are text where meaning matters; sales are structured numbers that need exact aggregation. Hybrid search would help find the SKU in text, but no search method can sum the units correctly.

Rule to remember: If queries mix exact codes with descriptions, use hybrid search; if the right result ranks too low, rerank; if the question needs totals over tables, give Claude a query tool.

3.7 · Evaluate connection protocols and select the appropriate integration mechanism (MCP, API/CLI, agent-to-agent)

Guide line: “Evaluate connection protocols and select the appropriate integration mechanism (MCP, API/CLI, agent-to-agent)”

In one sentence: Use MCP to share a capability with many AI clients, a direct API or CLI for one known call, and agent-to-agent when you hand a whole goal to someone else's agent.

The Model Context Protocol (MCP) is an open standard for exposing tools, data (resources) and reusable prompts to AI applications. A team builds one MCP server, and any MCP-capable client can use it: Claude Code, the Claude desktop app, agents built with the Claude Agent SDK, or the Claude API through its MCP connector. Servers can run locally or remotely. MCP pays off when the same capability is needed by several clients or teams, because it replaces one-off glue code with one shared, governed integration.

A direct API call is the lightest option: your application code calls a known service, or defines a tool in its own code that wraps that call. It fits one application with a fixed integration. A CLI (command-line tool) fits agents that have a shell, such as Claude Code: well-known tools like git or a cloud CLI are already familiar to the model and need no extra server. Building an MCP server for a single, fixed call inside one app adds moving parts for no reuse.

Agent-to-agent integration means delegating a goal, not a function call, to another autonomous agent that plans its own steps with its own tools and data, often owned by another team or company. Open protocols such as A2A define how agents describe themselves, accept tasks and return results. Choose it when the other side keeps its logic and systems private and runs a multi-step process itself. The general rule: pick the lightest mechanism that meets the reuse and ownership needs.

Know this

  • MCP standardises how tools, resources and prompts are exposed, so one server serves many AI clients.
  • MCP pays off when several clients or teams need the same capability.
  • A direct API call is simplest for one application with a fixed, known integration.
  • Agents with a shell can use familiar CLIs directly, without building a server.
  • Agent-to-agent delegates a goal to an autonomous agent that runs its own multi-step process.
  • Agent-to-agent fits when the other party owns the logic and won't expose its underlying systems.
  • Pick the lightest mechanism that satisfies reuse, ownership and security needs.

A partner offers simple, documented endpoints and no agentDirect API or an MCP wrapperThere is no agent to delegate to

Worked example

Situation: A bank's ticketing data must be searchable from Claude Code by developers, from the desktop app by support leads, and by two internal agents. Separately, a nightly script sends each day's new tickets to Claude once for a summary.

Decision: Build one MCP server for ticket search and read, used by all four clients. Keep the nightly summary as a direct API call in the script.

Why: Four clients share one capability, so MCP removes duplicated glue. The nightly job is a single fixed call; wrapping it in MCP would add a server to run for no benefit.

Rule to remember: If many AI clients need the same capability, build an MCP server; if one app makes a fixed call, call the API directly; if another party's agent runs the whole task, delegate agent-to-agent.

3.8 · Evaluate progressive discovery vs. monolithic context strategy

Guide line: “Evaluate progressive discovery vs. monolithic context strategy”

In one sentence: Load everything up front only when it is small, stable and always needed; otherwise start with a short index and fetch detail when the task calls for it.

A monolithic context strategy loads everything into every request: all instructions, all reference documents, all tool definitions. It is simple, predictable, and works well with prompt caching. But as it grows it costs more tokens, slows responses, and dilutes attention: with hundreds of similar tool definitions, the model is more likely to pick the wrong one.

Progressive discovery (also called progressive disclosure) starts with a short catalogue and loads detail only when needed. Claude's mechanisms include Skills, where only each Skill's name and description sit in context until a task calls for it, then its instructions and any extra files are read; tool search, where tool definitions are deferred and Claude searches for the few it needs; MCP resources, data a server offers to be read on demand; and simply letting an agent browse files.

Neither is always right. Progressive discovery adds a lookup step and a small chance of missing something relevant. Monolithic wins when the content is small, stable and needed on almost every request; then caching makes it cheap. Progressive discovery wins when the content is large, varied, and each task uses only a slice.

Short catalogue in context→Task arrives→Claude finds what it needs→Detail loaded→Task done with a lean context

Know this

  • Monolithic context is simple and cache-friendly, but grows costly and dilutes attention as content grows.
  • Progressive discovery keeps a short index in context and loads detail on demand.
  • Skills load only their name and description until needed, then their full instructions and files.
  • Tool search lets Claude find relevant tools from a large set instead of loading every definition.
  • MCP resources expose data a client can read when needed rather than preloading it.
  • Monolithic wins when content is small, stable and needed every time; prompt caching then makes it cheap.
  • A bigger context window does not fix tool confusion or attention dilution.

When the stem says…PickWhy

Worked example

Situation: A platform-engineering agent carries 150 tool definitions from five MCP servers and a 30-page runbook in every request. Typical tasks use three tools and one runbook section; replies are slow and it sometimes calls a similar but wrong tool.

Decision: Defer tool definitions behind tool search, and split the runbook into Skills by procedure, each with a clear description.

Why: Each task uses a small slice of a large, varied set, which is where progressive discovery wins. Caching the full context would cut cost and time to first token but would leave all 150 tools competing for the model's attention.

Rule to remember: If content is large and each task uses a slice, discover it progressively with Skills, tool search or resources; if it is small, stable and always needed, load it up front and cache it.
