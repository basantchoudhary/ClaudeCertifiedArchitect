Domain 4: Evaluation, Testing & Optimization

This domain is about proving that a Claude system works, finding out why it fails, and making it cheaper and faster without breaking it. Its questions ask you to pick the right metric, the right grading method, the right test, the first place to look when answers go wrong, and the optimisation lever that matches the bottleneck.

4.1 · Define evaluation metrics (accuracy, latency, cost, safety, security)

Guide line: “Define evaluation metrics (accuracy, latency, cost, safety, security)”

In one sentence: Before you build or change anything, write down what “good” means as numbers with targets, for accuracy, latency, cost, safety and security.

An evaluation metric is a number you can compute that tells you whether the system is doing its job. Without metrics, “the answers look good” is an opinion, and nobody can show whether a change helped or hurt. Anthropic's guidance is to define success criteria first: specific, measurable, achievable, and tied to what the business needs, such as “95% of invoices extracted with every field correct”.

Accuracy is task-specific. A classifier uses exact match. Extraction often uses F1, which balances precision (how many of the items found were right) and recall (how many of the right items were found). Open-ended text uses a rubric score from a human or a model judge. Latency is measured in percentiles: p50 is the median request, and p95 is the time that 95% of requests beat, which shows the slow tail that users complain about. Time to first token (TTFT) is how long until the first words appear, and it is what chat users feel. Cost is best measured per completed task, because an agent may make several calls and retries for one task.

Safety needs two rates: harmful outputs that get through, and legitimate requests that are wrongly refused. Security is measured by attacking the system: run a set of prompt-injection attempts and report the share that succeed, and test for data leakage. Keep each dimension separate with its own target. One blended score hides trade-offs, such as an accuracy gain that doubled the cost.

Business goal→Success criteria→One metric per dimension→Target for each→Measure on every change

Know this

  • Success criteria are written before building, and each one has a measurable target.
  • p95 and p99 latency show the slow tail; an average hides it.
  • Time to first token matters most for streamed chat; total time matters when a later step waits for the whole answer.
  • Cost per completed task is fairer than cost per call when an agent makes several calls or retries.
  • Safety is two rates that pull against each other: harmful outputs allowed and good requests refused.
  • Security metrics come from attack test sets, such as prompt-injection success rate.
  • A thumbs-up rate is a useful signal, but few users vote, so it cannot replace a task metric.

Worked example

Situation: A bank's back-office assistant extracts fields from loan documents. The team says accuracy is “great”, but cannot say which fields fail or what a document costs.

Decision: Define field-level exact match, an all-fields-correct rate per document, p95 latency, cost per document, and a leakage rate on documents with planted personal data, each with a target.

Why: Separate metrics show which field and which dimension needs work. A single blended score or user feedback would not help here: back-office users rarely rate outputs, and a blend hides a cost or leakage problem behind good accuracy.

Rule to remember: If you cannot say what “good” is as a number, define the metric and target before changing anything; if a stem mentions perceived speed, think time to first token, and if it mentions outside content, add a security metric.

4.2 · Design evaluation datasets and test frameworks using mixed methodologies

Guide line: “Design evaluation datasets and test frameworks using mixed methodologies”

In one sentence: Test on real, tricky and hostile examples, and grade each part with the cheapest method that grades it reliably: code, a calibrated model judge, or a person.

An eval dataset is a fixed set of inputs, each with a description of what a good output looks like. The trusted core is a golden set: examples sampled from real traffic and labelled by experts, so it matches what users actually send. Add edge cases (empty, very long, ambiguous or other-language inputs) and adversarial cases (injection attempts, requests the system must refuse). Keep a held-out part you never tune prompts against, so you notice when you have overfitted to the examples you stare at.

Mixed methods means each check uses the grader that suits it. Code-graded checks are fast, cheap and exact: valid JSON, required fields present, exact values, a citation included. LLM-as-judge means another model call scores the output against a written rubric; it scales to open-ended qualities like faithfulness and helpfulness. A judge must be calibrated: score a sample that humans have also labelled, and check that they agree, before trusting it. Judges have known biases, such as favouring longer answers, so the rubric should list specific criteria, and asking the judge to reason before giving its score helps.

Human review is the most trusted grader but slow and costly. Use it to label the golden set, to calibrate the judge, for high-stakes items, and for regular audits. Run the whole suite as a regression suite on every prompt, model or retrieval change, and add every production failure to it so the same bug cannot come back unnoticed.

Sample real traffic→Add edge and adversarial cases→Label with experts→Code checks, judge, human sample→Run on every change

Know this

  • A golden set drawn from real traffic beats invented examples because it has the real mix of requests.
  • More automatically graded cases usually beat a handful of hand-graded ones.
  • Use code-based grading for anything objective; it is exact and almost free.
  • An LLM judge needs a specific rubric and calibration against human labels, repeated whenever the rubric or judge model changes.
  • Judge biases include preferring longer answers and the first option shown; clear criteria and randomised order reduce them.
  • Every production failure becomes a new test case.
  • A held-out split shows whether prompt tuning has overfitted.

Worked example

Situation: An insurer's assistant writes 5,000 claim summaries a week. Each must include the claim number and amount, and must not state anything the claim file does not say. Two senior adjusters can review about 50 a week.

Decision: Code checks for the claim number, amount and format; an LLM judge with a faithfulness rubric for every summary; adjusters label 50 a week, used to calibrate the judge and audit it.

Why: Each grader does what it is best at. Human review alone covers 1% of the volume, and an overlap score such as ROUGE rewards copying words, not being faithful.

Rule to remember: If a check is objective, grade it with code; if it is open-ended and high-volume, use a rubric judge calibrated on human labels; if it is high-stakes or low-volume, have a person review it.

4.3 · Conduct A/B testing and iterative improvements

Guide line: “Conduct A/B testing and iterative improvements”

In one sentence: Prove a change offline on the eval set first, then test it on a share of live traffic against the current version, changing one thing at a time.

Improving an LLM system is a loop: find failures, form a guess about the cause, change one thing, measure, then keep or revert. One variable at a time matters because if you change the prompt and the model together and quality moves, you cannot tell which change caused it.

Offline evaluation runs the candidate on the fixed eval dataset. It is cheap, repeatable and safe, and it catches regressions before users see them, but it cannot show business outcomes such as sales or resolved tickets. Online A/B testing sends a random share of live traffic to the candidate (B) while the rest stays on the current version (A), and compares results over the same period. Split by user or conversation so one person does not flip between versions, and run until there is enough volume to tell a real difference from noise.

Decide before starting what you will compare: a primary metric, plus guardrail metrics such as cost, latency and safety that must not get worse, and the threshold to ship. Then ramp up gradually. When showing users a possibly worse answer is not acceptable, use a shadow test: the candidate runs on copies of live requests but users only see the current version's output. Shadow testing compares outputs, but it cannot measure how users react.

Hypothesis→Change one thing→Offline eval→A/B on a small share→Compare primary and guardrail metrics→Ramp up or revert

Know this

  • Change one variable per test, or the cause of any difference is unknown.
  • Run the offline eval before any live test; it catches regressions cheaply.
  • An A/B test needs a random split, the same time period, and enough volume.
  • Agree the primary metric, guardrail metrics and ship threshold before the test starts.
  • A win on quality that breaks a cost or safety guardrail is not a win.
  • Shadow testing shows outputs on live inputs without exposing users, but cannot measure user behaviour.
  • A few good-looking examples are an anecdote, not evidence.

Worked example

Situation: An online retailer's product Q&A assistant has a new prompt that adds size-guide advice. Offline it scores slightly higher. Marketing wants to know if it reduces returns.

Decision: Send 10% of shoppers, split by user, to the new prompt for four weeks; compare return rate as the primary metric, with cost per conversation and complaint rate as guardrails.

Why: Returns only show up in live behaviour, so the offline eval cannot answer the question. Comparing this month with last month on all users is tempting but confounded by season and promotions.

Rule to remember: If a change has not passed the offline eval, run it there first; if the question is business impact, A/B test one change on a random share of traffic with guardrails agreed up front.

4.4 · Diagnose system issues (prompt failure, hallucinations, model mismatch)

Guide line: “Diagnose system issues (prompt failure, hallucinations, model mismatch)”

In one sentence: When answers go wrong, check what went into the model first (the inputs and retrieved context), then the prompt, and only then the model.

There are three common failure types. A prompt failure means the instructions are unclear, incomplete or contradictory; signs are similar inputs handled differently, a drifting output format, or the model doing something reasonable that was not what you meant. A hallucination is a confident claim the context does not support; in a RAG system (retrieval-augmented generation, where documents are fetched and added to the prompt) it often happens because retrieval supplied wrong, stale or no relevant passages and the model filled the gap. A model mismatch means the model does not fit the task: either it is not capable enough (multi-step reasoning still fails with a clear prompt and the right context), or it is far more capable than a simple task needs, so you overpay.

Diagnose in order, because the cheap checks come first and most problems are upstream of the model. Open the traces (records of each step's inputs and outputs) for failing cases. If the needed fact is missing from the context, the problem is retrieval or data. If the fact is there but the answer ignores or contradicts it, look at the prompt: ask for quotes or citations, and explicitly allow “I don't know”. Only when the context is right and the prompt is clear should you run the failing cases on a more capable model.

Timing is a strong clue. A sudden change right after a document refresh, a deployment or a prompt edit points at that change. A pinned model version does not silently change. Lowering temperature reduces randomness, but it cannot supply a fact that is not in the context.

Collect failing cases→Inspect inputs and retrieved context→Check the prompt→Try a more capable model→Fix and add to the eval

Know this

  • Read the traces of real failures before changing anything.
  • Fact missing from the context points to retrieval or data; fact present but ignored points to the prompt.
  • Requiring supporting quotes and allowing “I don't know” reduce hallucinations.
  • Inconsistent handling of similar inputs is a sign of ambiguous instructions.
  • Confirm a model mismatch by running the same failing cases, with the same prompt and context, on a more capable model.
  • A sudden change usually follows something that changed: data, deployment or prompt.
  • Lower temperature makes output more consistent, not more correct.

Worked example

Situation: An HR policy assistant gives wrong leave entitlements for staff in a country the company just expanded into. Answers for other countries are fine.

Decision: Open traces for the failing questions. They show no passages from the new country's policy, because it was uploaded to a folder the indexer does not read. Add the folder, re-index, and add the cases to the eval.

Why: The failure is limited to new data, which points upstream. Switching to a stronger model is the tempting move, but no model can cite a policy it never received.

Rule to remember: If answers are wrong, look at the inputs and retrieved context first, then the prompt, then the model; if the fact is missing, fix retrieval, and if it is present but ignored, fix the prompt.

4.5 · Optimize token usage, latency, and cost-performance trade-offs

Guide line: “Optimize token usage, latency, and cost-performance trade-offs”

In one sentence: Find where the time and money go, apply the lever that matches that bottleneck, and rerun the eval to prove quality held.

The big cost levers are these. Prompt caching: put the stable part of the prompt (system prompt, tool definitions, long documents) first and mark it for caching; later requests that reuse the identical prefix read it from the cache at a fraction of the normal input price, and get their first token sooner. Model routing: send simple steps to a smaller, faster model and only hard ones to the most capable model. The Message Batches API: submit many requests to be processed asynchronously at about half the normal price, with results within 24 hours (most finish much sooner), for work nobody is waiting on.

Tokens drive both cost and time. Trim the context: send only the relevant chunks and summarise old conversation history. Cap the output with max_tokens and ask for concise formats; output tokens cost more than input tokens and are generated one at a time, so long answers are slow and expensive. For latency: make parallel calls for steps that do not depend on each other, so the total wait is the longest step, not the sum. Streaming shows the first words sooner, which improves perceived speed, but it does not reduce total time or cost.

Measure first: is the cost in input or output tokens, and which step is slow? Then pick the matching lever. Every optimisation is a trade-off, so rerun the eval after each change; a cheaper system that fails the quality bar is not an improvement.

Measure where tokens and time go→Pick the matching lever→Rerun the eval→Ship if quality holds

Know this

  • The Message Batches API costs about half the normal price and returns results within 24 hours, so it suits only work nobody waits on.
  • Prompt caching needs an identical prefix; anything that changes per request must come after the cached part.
  • Cached content expires after a short period without use, unless a longer lifetime is chosen.
  • Output tokens are priced higher than input tokens, so capping output saves both cost and time.
  • Streaming improves perceived latency only; it does not cut cost or total generation time.
  • Parallel calls cut wall-clock time for independent steps but use the same tokens.
  • Every optimisation is confirmed on the eval before it ships.

Worked example

Situation: A logistics firm classifies 80,000 delivery notes every night with the most capable model in real time. Results are read by the morning shift. The bill has tripled.

Decision: Move the job to the Message Batches API, cache the shared instructions, and test a smaller model on the eval; switch to it only if it meets the accuracy target.

Why: Nobody waits during the night, so half-price asynchronous processing costs nothing in usefulness. Cutting the instructions in half is tempting, but it risks quality and saves less than the batch discount.

Rule to remember: If nobody waits for the result, batch it; if the same prefix repeats, cache it; if independent steps run in series, parallelise them; and if quality is not re-checked, do not ship the optimisation.

4.6 · Monitor system performance using logging and observability tools

Guide line: “Monitor system performance using logging and observability tools”

In one sentence: In production, log every request with its prompt and model version, watch latency, errors, tokens, cost and sampled quality, and alert when they cross thresholds.

Offline evals tell you a version was good before release. Monitoring tells you it is still good on real traffic, which changes over time: new topics, new documents, new user behaviour. This change is called drift. Good logging records, for each request: an ID, the time, the prompt template version, the model version, the document index version, input and output tokens (including cache reads), latency (time to first token and total), the stop reason, tool calls and errors. Personal data in logs must be handled properly: redacted or access-controlled, with a set retention period.

Observability means you can answer new questions from that data. Traces link every step of one request (retrieval, each model call, each tool call), so you can see which step failed or was slow. Dashboards show p50 and p95 latency, error and rate-limit rates, tokens and cost per task, and cache hit rate. Quality needs its own check: an LLM system often fails with a normal, successful response that simply contains a wrong answer. So sample production outputs and score them with the same code checks and judge used offline, alongside user feedback, and alert on thresholds and trends.

Versions matter most. When quality drops, you group the metrics by prompt and model version and look for the step change at a release. Without versions in the logs, every complaint becomes a manual investigation. Failures found in production go back into the eval dataset.

Log each request with versions→Trace each step→Dashboards and sampled quality scores→Alerts→Failures into the eval set

Know this

  • Log the prompt version, model version and index version on every request.
  • Pin a specific model version so model changes are deliberate and visible.
  • Score a sample of production outputs with the offline graders; error rates miss wrong-but-successful answers.
  • Track cache-read tokens and cache hit rate; a sudden drop often means the cached prefix started changing.
  • Traces show which step of a multi-step request failed or was slow.
  • Redact or restrict personal data in logs rather than stop logging.
  • Alert on thresholds and trends, not only on errors.

Worked example

Situation: A pharmacy chain's assistant had three prompt updates and one model upgrade last month. Complaints rose, but the logs hold only request and response text.

Decision: Add prompt, model and index versions to every log record, score a daily sample with the offline judge, and chart quality per version with an alert on drops.

Why: The next drop can then be traced to its release in minutes. Rolling everything back is tempting, but it discards good changes without knowing which one was bad.

Rule to remember: If you cannot tell which change caused a drop, log prompt and model versions per request; if errors look normal but users complain, score sampled outputs for quality.

Practice

Practice 4.6.1 · Choose one.

A retailer's support assistant cost 35% more per day over two weeks, while conversation volume and answer length stayed flat. The dashboard shows only total tokens and cost per day. Two weeks ago a prompt change added the current time to the very start of the system prompt, ahead of the long cached instructions. What should the team look at first?

  1. The p95 latency of requests before and after the change.
  2. The judge's quality scores, grouped by prompt version.
  3. The daily number of retries and error responses.
  4. The cache-read tokens and cache hit rate per request.
Show answer

Answer: D. The deciding fact: something that changes on every request now sits at the start of the prompt, before the cached instructions. That breaks the identical prefix, so the cache stops hitting and every request pays full input price.

  • A ❌ Works as a related symptom, since lost caching also slows first tokens, but it does not explain cost directly.
  • B ❌ Works for quality problems, but the issue here is cost, with quality not in question.
  • C ❌ Works when retries inflate cost, but nothing points to errors, and the timing matches the prompt change.
  • D ✅ The cache-read tokens and cache hit rate per request.
Practice 4.6.2 · Choose one.

A bank's assistant answers account questions. Error rates and latency look normal, but complaints about wrong answers doubled this month. The logs store each request and response, but not which prompt template or model version served it. Three prompt updates shipped this month. What should the architect add first?

  1. An alert for when the error rate goes above its normal range.
  2. The prompt template version and model version on each logged request.
  3. A weekly manual review of ten conversations chosen at random.
  4. A rollback of all three of this month's prompt updates to last month's prompt.
Show answer

Answer: B. The deciding fact: three changes shipped and the logs cannot say which version served each answer. Versions per request let quality be grouped by release to find the bad change.

  • A ❌ Works for outages, but wrong answers return normally, so error rates stay flat.
  • B ✅ The prompt template version and model version on each logged request.
  • C ❌ Works as a spot check, but ten a week is too few, and without versions it cannot link problems to a change.
  • D ❌ Works as an emergency step if harm were severe, but it discards two possibly good updates blind.
