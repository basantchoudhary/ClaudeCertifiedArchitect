1.1 · Translate business problems into Claude-based AI solutions

Guide line: “Translate business problems into Claude-based AI solutions”

In one sentence: Start from the business outcome and its limits, then choose the simplest Claude design that meets them, and leave to plain code the parts that need no model.

Translating a business problem means turning a sponsor's goal (“cut loan-review time in half”) into a design: what goes in, what Claude does, what comes out, and how you will know it worked. The architect starts with the outcome and the constraints: volume, latency, budget, risk, data sensitivity and who must approve the result.

Next, split the problem into parts and ask of each part whether it needs a language model at all. Claude is strong at reading unstructured text, making judgements, drafting and summarising. A database query, a fixed rule or a calculation is cheaper, faster and exact, so those parts stay in ordinary code.

Then choose the simplest design that meets every constraint: often a single well-prompted call, sometimes with retrieval or a tool. Add more only when a stated requirement forces it. An answer that is impressive but ignores a constraint in the stem (cost, a human sign-off, data residency) is wrong however clever it is.

Business goal→Constraints and success measure→Split into parts→Model or plain code, per part→Simplest design that fits

Know this

  • Begin with the measurable outcome the sponsor wants, not with a model or a pattern.
  • Constraints (volume, latency, budget, risk, compliance) rule designs in or out before quality is compared.
  • Use Claude for unstructured language and judgement; use code, rules or queries for exact lookups and arithmetic.
  • A design should state its success measure up front so it can be evaluated later.
  • High-impact or regulated decisions usually keep a human approval step, and the design should say where it sits.
  • The simplest design that meets every stated constraint beats a more advanced one that misses any of them.

Mind map

When the stem says…PickWhy
Part of the task is an exact lookup or calculationPlain code, a query or a toolExact, cheap and testable, with no model guesswork
The task is reading messy text and making a judgementA Claude call with a clear promptThis is where a language model adds value
The answer depends on private or changing documentsClaude plus retrieval (an augmented LLM)The model needs the facts at request time
The decision is high-impact or regulatedClaude drafts, a person approvesKeeps accountability with a person
The steps cannot be known in advanceAn agentOnly then does the extra autonomy pay for itself

Worked example

Situation: A logistics company wants to cut the time staff spend answering “where is my parcel?” emails. Tracking status lives in a database; customers write in free text, often in several languages.

Decision: Claude reads each email and extracts the tracking number and the question; code looks up the status in the database; Claude drafts the reply in the customer's language. Emails it cannot interpret go to a human queue.

Why: Each part uses the right tool: language work for Claude, the exact status from the database. Letting Claude answer about status without the lookup would invent facts, and a fully autonomous agent would add cost and unpredictability the task does not need.

Rule to remember: If a part of the problem is exact (a lookup, a rule, a sum), give it to code; if it is language or judgement, give it to Claude, and stop at the simplest design that meets every stated constraint.

  2. A rules engine classifies each email by keywords and checks the limit, with no model involved.
  3. Claude classifies the email and extracts the amount; code compares it with the stored limit.
  4. An autonomous agent with database access decides the claim type and coverage in one loop.
Show answer

Answer: C. Deciding facts: the emails are free text (a language task for Claude) and the limit sits in a database (an exact comparison for code). Each part goes to the tool that does it best.

  • A ❌ Works, but it asks the model to judge a number that code can compare exactly; it would fit if limits existed only in prose policy wording.
  • B ❌ Works, but keyword rules struggle with free-text emails; it would fit if claims arrived on a fixed form.

1.2 · Design end-to-end architectures (input → processing → output → feedback loops)

Guide line: “Design end-to-end architectures (input → processing → output → feedback loops)”

In one sentence: Design all four stages, input, processing, output and feedback, so the system can be checked and improved after launch, not just built.

An end-to-end architecture follows a request from start to finish. Input covers where data comes from, how it is validated and cleaned, and what is rejected. Processing is the model call with its prompts, tools and retrieval. Output covers the format, the checks (for example validation against a schema, which is a formal description of the required fields and types) and how the result reaches a person or another system.

The fourth stage, the feedback loop, is the one most often missing. It captures what happened after the output: user corrections, ratings, escalations and business outcomes. Those signals feed an evaluation set (a fixed collection of test cases with known good answers), monitoring dashboards and the next round of prompt or retrieval changes.

Without feedback, quality can drift silently: documents change, users ask new kinds of questions, and nobody notices until someone complains. Checks between stages matter too. Validating input early is cheaper than repairing bad output later, and an output check catches format errors before they reach a downstream system.

Input: collect and validate→Processing: prompt, tools, retrieval→Output: check and deliver→Feedback: corrections and outcomes→Evals and improvements

Know this

  • Every design should name all four stages; an option that leaves out feedback is usually incomplete.
  • Validate and clean input before it reaches the model, and reject what the system cannot handle.
  • Check output in code (schema, required fields, allowed values) before it is delivered to another system.
  • Human corrections are the richest feedback: store the original output beside the corrected one.
  • Feedback should flow into the evaluation set, so each later change is tested against real failures.
  • Monitoring watches the live system and evaluation tests a change before release; a full loop needs both.

Mind map

When the stem says…PickWhy

Blank or unsupported files cause invented answersValidate at the input stageCheaper to reject early than to repair later
A downstream system breaks on bad formatsValidate output against a schema in codeCatches errors before delivery

One known case fails because the prompt is plainly wrongFix the prompt, then add the case to the evalsA direct defect is fixed directly; the loop stops it coming back

Worked example

Situation: A contract-summary tool went live six months ago. Legal staff now edit most summaries by hand, but the team only learned this from a manager's complaint.

Decision: Store each generated summary with its edited version, turn the differences into eval cases, track the edit rate as a quality metric with an alert, and test every prompt change against the eval set before release.

Why: The defect is the missing loop, not one bad prompt. Tuning the prompt once more would help for a while, but the next drift would again go unseen.

Rule to remember: If quality drifts unseen, add the feedback loop; if bad data gets in, validate input; if bad formats get out, validate output in code.

1.3 · Select appropriate architectural patterns (workflow, agentic, augmented LLM)

Guide line: “Select appropriate architectural patterns (workflow, agentic, augmented LLM)”

In one sentence: Pick the least autonomy that solves the problem: an augmented LLM for one-step tasks, a workflow when the steps are known, and an agent only when they are not.

Anthropic's guidance on building effective agents describes a ladder of patterns. The base is the augmented LLM: one model call enhanced with retrieval, tools or memory. Many products need nothing more, for example answering a question from company documents.

A workflow runs model calls along paths fixed in code. Common shapes are prompt chaining (each step feeds the next, with checks between), routing (classify the input, then send it to a specialised prompt or model), parallelisation (split independent parts, or run the same task several times and compare), orchestrator-workers (a central model breaks a task into subtasks it decides at run time, then combines the results) and evaluator-optimizer (one call drafts, another critiques against clear criteria, and the loop repeats until the draft passes).

An agent lets the model choose its own steps and tools in a loop, using feedback from each step, until the goal is met. Agents suit open-ended problems where the number and order of steps cannot be predicted. They cost more, take longer and are harder to predict and test, so use them only when the task needs that flexibility, and give them stopping conditions such as a step limit, plus guardrails.

Augmented LLM: one call plus tools→Workflow: paths fixed in code→Agent: the model picks its steps

Know this

  • Augmented LLM: a single call with retrieval, tools or memory; the building block of every other pattern.
  • Workflow: the code decides the steps, so it is predictable, testable and cheaper.
  • Agent: the model decides the steps in a loop, so it is flexible but costlier and less predictable.
  • Routing fits inputs that fall into distinct categories that are better handled separately.
  • Evaluator-optimizer fits tasks with clear quality criteria where a critique measurably improves the next draft.
  • Orchestrator-workers differs from parallelisation because its subtasks are decided at run time, not fixed in advance.
  • Start with the simplest pattern, and add autonomy only when evaluation shows the simpler one falls short.

Mind map

When the stem says…PickWhy
One question, answered from documentsAugmented LLM with retrievalThere is no sequence of steps to manage
Every item goes through the same known stepsWorkflow: prompt chainingA fixed order is predictable and testable
Inputs fall into distinct types that need different handlingWorkflow: routingEach type gets its own tuned prompt or model
A draft must meet clear criteria, and critique helpsWorkflow: evaluator-optimizerRepeated refinement against a checkable standard
The next step depends on what was just foundAgentOnly a model-directed loop can change the path as it goes

Worked example

Situation: A software firm wants help with two jobs: translating release notes into five languages, and investigating customer-reported bugs whose cause could be anywhere in the codebase.

Decision: Release notes use a workflow: translate into the five languages in parallel, then run a terminology check. Bug investigation uses an agent with read access to the code, logs and tests, and a step limit.

Why: The translation steps are known in advance, so an agent would add cost and unpredictability. Bug investigation cannot be scripted because each finding decides the next step, so a fixed workflow would miss causes.

Rule to remember: Pick the least autonomy that solves the problem: one answer from documents gets an augmented LLM, fixed steps get a workflow, and open-ended work gets an agent.

1.4 · Design multi-agent systems and orchestration strategies

Guide line: “Design multi-agent systems and orchestration strategies”

In one sentence: Use several agents only when the work splits into independent or specialist parts; then use a coordinator, give each agent narrow tools and pass it its context explicitly.

A multi-agent system uses more than one model-driven agent, each with its own instructions, tools and context. The usual shape is hub-and-spoke: a coordinator (also called an orchestrator) breaks the goal down, hands subtasks to subagents, and combines their results. Subagents do not share the coordinator's memory; they see only what they are given.

Multi-agent designs pay off in two cases. Parallel breadth: many independent threads, such as researching ten competitors at once, where each subagent explores in its own fresh context window. Specialisation: parts that need different tools, permissions or instructions, such as a code reviewer that must not have deploy rights. The costs are real: many more tokens, extra latency for coordination, and more places for things to go wrong.

So the default is one agent with good tools, and multi-agent is chosen when the stem shows parallel or specialist value. When you do choose it, scope each subagent's tools to its role, put the background and the required output format in each subagent's brief, have the coordinator check results before merging, and trace every call across agents so a failure can be located.

Coordinator receives the goal→Splits it into subtasks→Subagents work in parallel with scoped tools→Coordinator checks and merges→Final answer

Know this

  • Hub-and-spoke: one coordinator assigns work and merges results; subagents do not talk to each other directly.
  • Subagents start with fresh context, so anything they need must be passed in their task description.
  • Multi-agent systems use many more tokens than a single agent, so the value of the task must justify the cost.
  • Parallel subagents suit breadth-first work with independent parts; tightly linked steps suit one agent.
  • Scoping each subagent's tools to its role is also a security boundary.
  • Trace calls across all agents with one request ID, or failures cannot be located.

Mind map

When the stem says…PickWhy
One user goal, a handful of tools, steps that depend on each otherA single agentCoordination would add cost with no gain
Many independent research threadsCoordinator with parallel subagentsBreadth runs in parallel, in separate contexts
One part needs permissions the others must not haveA separate specialist subagentIsolates tools and access by role

Worked example

Situation: A consulting firm writes due-diligence reports on acquisition targets: financials, legal cases, news, patents and leadership, each from different sources. Analysts wait two days for each report.

Decision: A coordinator splits the report into five research areas and launches one subagent per area, each with only that area's search tools and a clear brief and output format. The coordinator then checks and merges the findings.

Why: The five areas are independent and benefit from parallel work in separate contexts. A single agent would work through them one by one and fill its context. The extra token cost is justified by a two-day wait on a high-value report.

Rule to remember: If the work splits into independent or specialist parts, use a coordinator with scoped subagents and full briefs; if the steps depend on each other, keep one agent with good tools.

1.5 · Apply decomposition techniques for complex problem solving

Guide line: “Apply decomposition techniques for complex problem solving”

In one sentence: Break a large task into smaller steps you can check one at a time, using a fixed plan when the steps are known and an adaptive plan when they are not.

Decomposition means splitting a complex task into smaller subtasks, each with a focused prompt and a clear output. One huge prompt that extracts, analyses and writes at once tends to do each part less well, and when it fails you cannot tell which part broke.

Fixed decomposition is used when the steps are known in advance. Prompt chaining runs them in order, with a check between steps (often called a gate) so a bad intermediate result is caught early. For large inputs, a common fixed shape is per-item passes, then an integration pass: review each file or section on its own, then run one pass that looks across all of them, for example for contradictions or knock-on effects.

Adaptive decomposition is used when the steps depend on what is found. The model makes a first plan, works on it, and revises the plan as findings arrive, as in orchestrator-workers or an agent. Either way, each step's output should be small and checkable, and later steps should receive exactly the context they need.

Complex task→Split into focused steps→Run one step→Check its output→Pass it to the next step→Integrate the results

Know this

  • A focused prompt per step usually beats one long prompt that does everything.
  • Checks between steps catch bad intermediate output before it spreads.
  • Per-item passes plus an integration pass give each item full attention and still catch issues that cross items.
  • Fixed decomposition suits known, repeatable steps; adaptive decomposition suits investigation.
  • Decomposition makes failures easier to locate, because each step can be evaluated on its own.
  • More steps add latency and cost, so split only where a step needs separate focus or checking.

Mind map

When the stem says…PickWhy
One prompt does extraction, analysis and writing, and quality is unevenA prompt chain with checks between stepsEach step gets full attention and can be tested
Reviewing a forty-file change misses issuesPer-file passes, then an integration passDepth on each file plus a cross-file view
The plan depends on what the first findings showAdaptive decompositionA fixed chain cannot follow new leads
A simple task is already done well by one promptKeep the single promptExtra steps would only add latency and cost

Worked example

Situation: A pharma team asks Claude to review 60 clinical-trial site reports and produce one risk summary. A single prompt over all 60 reports misses issues in the middle and gives shallow comments.

Decision: Run one pass per site report with a fixed checklist and structured output, validate each result, then run an integration pass over the structured results to find patterns across sites and write the summary.

Why: Per-report passes give each report full attention, and the integration pass still catches patterns across sites. A bigger context window would hold all 60 reports but would not fix the spread-thin attention.

Rule to remember: If the steps are known, chain focused prompts with a check between each; if one input is too big to review well, do per-item passes and then an integration pass; if the steps depend on findings, decompose adaptively.

1.6 · Align solutions to business value pillars (efficiency, transformation, productivity, cost, performance SLAs)

Guide line: “Align solutions to business value pillars (efficiency, transformation, productivity, cost, performance SLAs)”

In one sentence: Justify each design by the business value the sponsor cares about most, and measure that value, not just technical quality.

Sponsors fund AI for different reasons. The guide names five value pillars. Efficiency: the same work done faster or with less effort. Transformation: something that was not possible before, such as a new service. Productivity: people achieve more in the same time. Cost: a lower cost per outcome. Performance SLAs: meeting agreed service levels (an SLA, or service-level agreement, is a promised target) for latency, availability or quality.

The pillar shapes the design. A cost-focused sponsor wants the cheapest configuration that meets a quality bar, perhaps a smaller model with prompt caching and batch processing. An SLA-focused sponsor wants predictable latency, perhaps a fast model and streaming on the live path. A transformation goal can justify a more capable, more expensive design, because the value is something new, such as new revenue.

Then choose a metric for that pillar and record a baseline before launch: cost per resolved ticket, handling time, cases per analyst per day, or p95 latency (the time within which 95 percent of requests finish). Technical metrics such as accuracy still matter, but as guardrails: a design must not save money by breaking quality.

Know this

  • Efficiency: the same output with less time or effort.
  • Transformation: a new capability, product or service that was not feasible before.
  • Productivity: more output per person, often by assisting rather than replacing the work.
  • Cost: a lower cost per unit of outcome, always paired with a quality floor.
  • Performance SLAs: agreed targets for latency, availability or quality, usually measured at a percentile.
  • Measure a baseline before launch so the value can be shown afterwards.

Worked example

Situation: A telecom sponsor wants to cut the cost per resolved support chat by 30 percent while keeping customer satisfaction at today's level. The team favours the most capable model with extended thinking on every chat.

Decision: Route simple chats to a smaller, cheaper model and send only complex ones to the capable model; cache the shared policy prompt. Track cost per resolved chat against a baseline, with satisfaction as a guardrail metric.

Why: The pillar is cost with a quality floor. The team's favourite design might score slightly higher on quality, but it would raise the cost per chat and miss the sponsor's goal.

Rule to remember: If the sponsor wants lower cost, pick the cheapest design that meets the quality floor; if they want an SLA, design for the latency target; if they want something new, judge it by adoption; and always measure that pillar against a baseline.

Practice

Practice 1.6.1 · Choose one.

A hospital network's sponsor gives one goal for a discharge-summary assistant: nurses should complete more discharges per shift without extra staff. Two candidate designs score the same on accuracy. Which success measure should the architect put at the centre of the business case?

  1. Cost per summary, compared with the current transcription service.
  2. The p95 time to generate a summary, against a two-second target.
  3. Discharges completed per nurse per shift, against a baseline.
  4. The number of new patient services the hospital can now offer.
Show answer

Answer: C. Deciding fact: the goal is more output per nurse, which is the productivity pillar. The measure must match that pillar and have a baseline so the gain can be shown.

  • A ❌ Works for a cost goal, but the sponsor did not ask to save money.
  • B ❌ Works for a performance SLA, but fast summaries do not show nurses are doing more.
  • C ✅ Discharges completed per nurse per shift, against a baseline.
  • D ❌ Works for a transformation goal, but this sponsor wants more of today's work done.
Practice 1.6.2 · Choose two.

A retailer's sponsor sets two goals for a product-question assistant: answers within two seconds for 95 percent of requests, as promised in a partner contract, and a lower cost per answer than today's human team. Which two design choices best serve these goals?

  1. Send every answer through a second model call that verifies it before sending.
  2. Use the most capable model with extended thinking on every request.
  3. Process the questions in overnight batches at a discounted price.
  4. Use a smaller, faster model that passes the eval, routing hard queries to a larger one.
  5. Cache the long, unchanging product-policy prefix that every request shares.
Show answer

Answer: D and E. Deciding facts: a latency SLA plus a cost goal. A fast model that passes the eval serves both, and caching the shared prefix cuts both input cost and time to first token.

  • A ❌ Works to raise accuracy, but a second call adds latency and cost, against both goals.
  • B ❌ Works for hard reasoning, but it is slower and costlier, against both goals.
  • C ❌ Works for cost, but overnight answers break the two-second promise.
  • D ✅ Use a smaller, faster model that passes the eval, routing hard queries to a larger one.
  • E ✅ Cache the long, unchanging product-policy prefix that every request shares.
