Large codebase exploration

A long Claude Code session in a big codebase starts to blur what it found in the morning. The tempting answers keep everything in the session: read more files, remind Claude, get a bigger window, or restart and hope. The exam wants the findings to live somewhere the context can't blur: written down, with the noisy searching done elsewhere.

D5 Context Management & ReliabilityExam guide 5.4About 12 minutes

At a glance: in a long codebase exploration, save key findings to a scratchpad file, send verbose exploration to subagents, and use /compact when the context fills.

Start here: the detective's board

A detective works a long case with hundreds of files.

Trust memory. By the third day, “the suspect left at 9:40” has become “some time in the evening, as these things usually go”. Asked twice, the detective gives two different times.
Pin it to the board. Every confirmed fact goes on the board with where it came from. Juniors sift the boxes of paper and come back with one paragraph each. Every so often, the desk is cleared. Days later, the board still says exactly what was found.

Claude Code works the same way. Everything Claude reads sits in its context window, the working memory for one session. In a long session that memory gets crowded, and the exam guide names the signs of context degradation: inconsistent answers, and talk of “typical patterns” instead of the specific files found earlier. Four habits fix it:

  • A scratchpad file is the board: Claude writes each key finding, with file and line, to a file on disk, and reads it back when needed.
  • A subagent is the junior: it runs the broad search in its own context and returns a short summary, so the verbose output never enters the main session.
  • /compact clears the desk: it condenses the conversation so far, freeing room.
  • A manifest is a structured state file (findings, modules done, modules left, next step) so a crashed session can pick up exactly where it stopped.
The one question to ask: is the session starting to forget or blur what it found earlier, and where should those findings live instead?
  • Answers drift to “typical patterns” or contradict earlier ones: write confirmed findings to a scratchpad file.
  • Searches dump thousands of lines: send them to a subagent that returns only what matters.
  • The context is nearly full, answers still accurate: /compact now, before they blur.
  • The work must survive a crash or carry on tomorrow: a manifest of findings and progress, read on every restart.
  • Read more, remind Claude, bigger window, restart: each keeps the findings in the context, or throws them away.

Words in the question that tell you which side you're on

Scratchpad or manifest

  • “inconsistent answers”
  • “typical patterns” instead of the file it named
  • “forgot an earlier finding”
  • “session crashed”, “pick up tomorrow”

Subagents or /compact

  • “verbose output”, “thousands of lines”
  • “searching hundreds of files”
  • “context nearly full”
  • “long exploration”

The four traps

TrapWhat the wrong option looks likeWhy it loses
Fills context“Read every file in the module up front so nothing is missed”Fine on a small module. On a large codebase it floods the context, and the earlier findings degrade.
Loses findings“Restart the session whenever answers get inconsistent”It clears the clutter, but without a saved record the new session starts from nothing.
Delays the problem“Switch to a model with a bigger context window”It works for a while, then the same degradation returns later in the run.
Only usually works“Ask Claude to keep earlier findings in mind”An instruction isn't storage. The findings still live only in the context, and still fade as it grows.

Rule to remember

Write findings down, delegate the noisy searching, and compact the rest.
