Resume, fork or start fresh?

You come back to work Claude started earlier. Every option on the exam is a real way to carry on, and each one is right somewhere. The trap is picking the one that suits a different situation: resuming when the code has moved on, starting over when nothing changed, or trying two ideas one after the other in the same session.

D1 Agentic ArchitectureExam guide 1.7About 12 minutes

At a glance: resume when nothing has changed, fork to try another approach from the same starting point, and start a new session with a summary when the earlier tool results are out of date.

Start here: the bookmark, the photocopy and the fresh notes

You are reading a long book, with notes in the margins.

Pick up where you left off. Nobody touched the book. Open it at the bookmark; your notes still match the page.
Photocopy the page. You want to try two different notes on the same page. Copy it, write one note on each copy, compare.
Start from fresh notes. Someone rewrote three chapters while you were away. Your margin notes now describe pages that no longer exist. Write down what you still know on one sheet, then reread the changed chapters.

Claude's sessions work the same way. Everything Claude read in a session is kept as tool results: snapshots of the files as they were when it read them. Snapshots don't update when the code does.

  • --resume <session-name> reopens a named session with its whole history, snapshots included. It is the bookmark.
  • fork_session makes independent branches from one shared starting point. Each branch has the full history; neither sees the other's work. It is the photocopy.
  • A new session with a structured summary starts clean, seeded with a short, organised list of findings, decisions and what is left. It is the fresh notes. A structured summary means headed sections, not a paragraph of prose.
The one question to ask: is what the old session saw still true, and do you want one path or two?
  • Still true, one path: --resume <session-name>. Keep everything it learned.
  • Still true, two paths (try two approaches, compare options): fork_session, one branch per approach.
  • Mostly no longer true (many files changed, a refactor, or you can't say which files moved): a new session seeded with a structured summary, then re-read what changed.
  • Mostly still true, a small known change (one or two files you can name): resume and tell the agent which files changed. It keeps every finding that still holds and re-reads just those files.

To tell these two apart, ask how much of what the session learned is now wrong. If only a little, and you know which part, correct it by naming the files. If a lot, or you can't tell, start clean from a summary.

Words in the question that tell you which side you're on

Resume

  • “continue yesterday's session”
  • “nothing has changed”, “nobody has touched”
  • “named session”
  • “pick up where it left off”

Fork

  • “try two approaches”
  • “compare options”
  • “from the same starting point”
  • “keep the better one”

Fresh, with a summary

  • “files changed since”
  • “a teammate merged”, “refactored”
  • “stale tool results”
  • “results are out of date”

    The three traps

    TrapWhat the wrong option looks likeWhy it loses
    Stale results“Resume the session and carry on” after a merge or refactor; forking a session whose snapshots are out of dateThe old tool results still describe the old code. Telling the agent what changed helps, but a fresh session with a structured summary is more reliable.
    Wastes work“Start a new session and explore again”, or a summary, when nothing has changedIt works, but it throws away context that was still true and repeats the exploration.
    Polluted context“Try approach A, then approach B in the same session”The first attempt's reasoning colours the second. A fork gives each approach a clean branch from the same start.

    Rule to remember

    Same world, resume. Two paths, fork. Changed world, start fresh with a summary.
