Explicit criteria

A review bot flags too much, and developers stop reading it. The tempting answers ask Claude to be more careful: “be conservative”, “only report high-confidence findings”, a second pass to double-check. The exam's answer is to tell Claude exactly what counts as a finding, and what each severity level looks like in code.

D4 Prompt Engineering & Structured OutputExam guide 4.1About 15 minutes

At a glance

To cut false positives, give categorical criteria such as “flag a comment only when it contradicts the code”. Telling Claude to “be conservative” or to report “only high-confidence” findings doesn't raise precision.

Start here: the guard at the door

An office hires a new security guard for the front door.

“Be careful who you let in.” The guard stops the courier, the cleaner and a visitor in a suit, and waves through someone who looked confident. Telling them to be more careful just means more people stopped, for the same fuzzy reasons.
“Let in anyone with a blue badge. Stop anyone without one.” Now the guard knows exactly what counts. Add “visitors sign the book; contractors call facilities”, and every case has a clear action.

A review bot is the guard. A false positive is a finding that isn't a real problem, like a typo flagged as an “inaccurate comment”. Precision is the share of posted findings that are real. A mood word (“careful”, “conservative”, “confident”) doesn't tell Claude what counts, so the same kinds of noise keep coming. Explicit criteria (also called categorical criteria) do: they name what to flag, what to skip, and what each severity level looks like.

The noise also spreads. Developers don't read a review one category at a time. When half the comments are about typos, they skim the whole review, including the security finding that mattered.

The one question to ask: does the fix tell Claude exactly what counts, or only how cautious to feel?
  • Only how cautious (“be conservative”, “only high-confidence”, “be more careful”, a second pass with the same rule): precision barely moves. Claude is confident about the wrong things.
  • Exactly what counts: name what to flag and what to skip (“flag a comment only when its claimed behaviour contradicts the code”), and define each severity level with a concrete code example. This is the exam's answer.
  • The category is noisy but catches real bugs: rewrite its criteria. Don't switch it off.
  • The rule is already clear, but the format or the borderline calls vary: that is a different trap. Add a few examples (see Few-shot examples).

Words in the question that tell you which side you're on

Points to explicit criteria

  • “too many false positives”
  • “developers ignore the findings”, “skip its output”
  • “a noisy category”, “flags things that are fine”
  • a vague rule: “check comments are accurate”, “flag anything questionable”

Words in tempting wrong options

  • “be conservative”
  • “only high-confidence”
  • “be more careful”, “use your judgement”
  • “switch the category off”, “a second instance confirms each finding”

Developer trust in the review /100

The behaviours and the trust figures are illustrative, chosen to show the shape. They are not measurements, and every run is the same. Trust here starts at 100 and drops 5 points per false positive and 4 per wrong severity. The exam guide's points are that explicit criteria beat vague instructions, that confidence wording doesn't improve precision like categorical criteria, and that a high false-positive category erodes trust in the accurate ones.

The four traps

TrapWhat the wrong option looks likeWhy it loses
Confidence wording only usually works“Be conservative”; “report only findings you are highly confident about”It says how cautious to be, not what counts. Claude is confident a typo is a typo, so the same kinds of noise stay.
Switch the category off delays the problemDrop the noisy category until its precision improvesThe noise goes, and so do the real bugs in that category. Explicit criteria keep the category and remove the noise.
A second pass overbuiltA second Claude call or instance double-checks each finding before it is postedIt re-checks against the same vague standard, for many more calls. Fix what gets flagged in the first place.
Examples for a vague rule different problemAdd a few example findings to the promptExamples mainly fix inconsistent format and borderline calls. When the flagging rule itself is vague, state the criteria first.

Rule to remember

Tell Claude exactly what to flag; telling it to be careful doesn't cut false positives. Name what to flag and what to skip, and define each severity with a concrete code example.

Exam guide 4.1: “Explicit criteria beat vague instructions ("flag comments only when claimed behavior contradicts actual code" vs "check comments are accurate").” “"Be conservative" / "only high-confidence" don't improve precision like categorical criteria.” “High false-positive categories erode developer trust in accurate ones; define explicit severity criteria with concrete code examples.”
