Plan or just do it?

Claude Code can plan before it edits, or it can just make the change. The trap runs both ways. For a big change whose approach isn't settled, the wrong answers start editing straight away. For a one-line fix, they wrap it in plans, searches and questions. Learn to size the task first, and the right mode follows.

D3 Claude Code ConfigurationExam guide 3.4 and 3.5About 15 minutes

At a glance: Make a small, settled change directly; use plan mode for big, many-file or undecided changes, and send long searches to the Explore subagent.

Start here: hanging a picture, or redoing the kitchen

Think about two jobs at home.

Hang one picture. You know the wall, you have the nail. You just do it. Drawing a plan or calling a meeting first would only waste the afternoon.
Redo the kitchen. Walls, pipes, wiring, and two ways it could be laid out. You measure every room and agree the layout before anyone knocks down a wall. Knocking first means building some of it twice.

Claude Code works the same way. Direct execution is hanging the picture: Claude makes the change and runs the tests. Plan mode is the kitchen: Claude explores the code and proposes a plan, and nothing changes until you approve it. Three helpers fit around them:

  • The Explore subagent is the person you send to measure every room. They come back with one sheet of numbers, not a pile of notes.
  • The interview pattern is asking the family what they want before drawing anything: Claude asks you questions first.
  • Tests first is marking where the cupboards must go with tape on the floor. Each attempt is checked against the marks, and Claude sees exactly which ones it missed.
The one question to ask: is the approach already decided, and is the change small?
  • Yes (a typo, one validation check, a known file): direct execution. Just do it.
  • No: many files, more than one valid approach, or an architectural decision: plan mode first.
  • The plan needs a lot of searching first: send it to an Explore subagent, so only a summary lands in the session.
  • Nobody has said exactly what's wanted: the interview pattern. Claude asks before it builds.
  • The right answers are known, but fixes keep breaking other cases: tests first, then share the failures.

Words in the question that tell you which side you're on

Just do it

  • one, single, a check, a typo, a rename
  • “the file is known”, “the format already exists”
  • the ticket already states the rule
  • “quickest”, “most efficient”

Plan first

  • many files, folders, screens or services
  • migrate, restructure, replace, split
  • “two libraries”, “engineers disagree”, “not yet chosen”
  • “nobody has mapped…”, “how should they start?”

    The minutes and context figures are illustrative, chosen to show the shape. They are not measurements. The exam guide's point is that plan mode prevents rework on big or open changes, and that a simple, well-scoped change needs no plan.

    Things to try: typo + plan mode, then typo + direct execution. Then library move + direct execution to watch the rework pile up, and library move + plan mode, then + Explore subagent to see the context meter drop. Last, CSV export + plan mode: a good plan built on a guess.

    Rule to remember

    Small and settled → just do it. Big or undecided → plan first. Long searches go to the Explore subagent; unclear asks get an interview; known answers become tests.

    Exam guide 3.4: “Plan mode: large-scale changes, multiple valid approaches, architectural decisions, multi-file mods.” “Direct execution: simple well-scoped changes (single validation check).” “Plan mode enables safe exploration/design before committing → prevents rework.” “Explore subagent isolates verbose discovery output, returns summaries.” Exam guide 3.5: “Test-driven iteration (write tests first, share failures); the interview pattern (Claude asks questions first)”.
