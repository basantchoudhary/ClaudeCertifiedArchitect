Stop reason

Every agent runs a loop: ask Claude, run the tool it asks for, ask again. The trap is in how the loop decides to stop. The wrong options all stop on something that looks like a signal (some text, a polite closing line, a turn count) instead of the one field the API gives you for exactly this: stop_reason.

D1 Agentic ArchitectureExam guide 1.1About 15 minutes

At a glance: keep the loop going while stop_reason is "tool_use" and stop when it is "end_turn"; never stop because of the reply's wording or an iteration cap.

Start here: the waiter and the menu

A waiter keeps going back to the kitchen while the customer is still ordering, and stops when the customer closes the menu. The waiter does not stop because the customer said “great” halfway through, and does not stop after exactly three trips.

Claude's API tells your code the same thing in one field. Every response carries a stop_reason: a short label saying why Claude stopped writing. "tool_use" means “I want a tool run; send me the result”. "end_turn" means “I'm finished with this turn”. Your loop (the code that keeps calling Claude) reads that label after every call, and nothing else decides when it stops.

The one question to ask: what does the code look at to decide whether to run another step: the stop_reason field, or something else?
  • stop_reason: right. Continue on "tool_use", stop on "end_turn".
  • Any text in the reply: wrong. Claude often writes a short line and asks for a tool in the same reply.
  • The wording (“done”, “task complete”, “Anything else?”): wrong. Wording varies.
  • A turn counter: fine as a safety net, wrong as the main stop.

Words in the question that tell you which side you're on

Points to reading stop_reason

  • “loop ends too early”, “loop never ends”
  • “decide when the agent is done”
  • “after each response”
  • “tool results”

Points to the trap

  • “checks the reply for ‘done’”
  • “looks for phrases like ‘I have finished’”
  • “stops after 10 iterations”
  • “if the response contains text”

The traps

  

    
TrapWhat the wrong option looks likeWhy it loses

    
Text as a stop signStop as soon as the response includes any textClaude often writes text and asks for a tool in the same response, so the loop ends before the tool runs. The exam guide names this anti-pattern.

    
Parsing the wordingStop when the reply contains a phrase such as “task complete”Only usually works. Wording varies, so the loop sometimes stops mid-task or runs on. The field exists so you don't have to parse text.

    
Cap as the main stopStop after a fixed number of iterations, such as 10Cuts off long tasks and wastes calls on short ones. A cap is only a safety net.

    
Different problemReplace the loop with a fixed sequence of tool callsIt removes Claude's ability to choose the next step from what it just learned. It answers a design question, not a stopping one.

Rule to remember

  

    The loop's stop sign is stop_reason: keep going on “tool_use”, stop on “end_turn”. Not the text, not the wording, not a counter.
    
Exam guide 1.1: “Continue the loop when stop_reason == "tool_use"; terminate when "end_turn".” And: “Anti-patterns: parsing natural-language signals to determine termination; arbitrary iteration caps as the primary stop; checking assistant text content as a completion indicator.”
