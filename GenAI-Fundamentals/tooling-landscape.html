1 · Observability & tracing landscape

LLM observability is ordinary distributed tracing plus three things ordinary APM does not capture: the prompt and response, token usage and cost, and a quality score. That last one is why generic APM alone is rarely enough — it can tell you the call took 900 ms, not that the answer was wrong.

Default: instrument with OpenTelemetry, and send it to Langfuse (or your existing APM if one is mandated). That keeps the instrumentation portable and makes the backend a reversible decision — which is the only property that reliably survives a two-year tool cycle.

2 · OpenTelemetry and its alternatives trade-off

Worth being precise, because the question is usually asked wrongly: OpenTelemetry is a standard, not a product. Its true alternatives are proprietary agents. The LLM-specific libraries people name as alternatives are mostly conventions built on top of it.

Option Relationship to OTel Trade-off Choose when
OpenTelemetry + GenAI semantic conventionsOSS The standard itself Vendor-neutral, huge ecosystem; GenAI conventions are still settling, so expect some churn Default. Especially if the backend may change.
OpenLLMetry (Traceloop)OSS On top of OTel Auto-instruments LLM SDKs and emits OTel spans — not a replacement You want LLM spans without writing them
OpenInference (Arize)OSS On top of OTel Alternative span conventions for LLM/RAG; pairs with Phoenix You use Phoenix or want richer RAG spans
Vendor SDKs — Datadog, New Relic, Dynatrace OneAgent, Elastic APMcommercial True alternatives Deeper out-of-the-box features and support; re-instrumenting later is real work The vendor is mandated and unlikely to change
SentryOSS + SaaS Alternative, with OTel support Error-first rather than trace-first Exceptions matter more than latency
Prometheus + StatsDOSS Metrics only No traces — cannot answer "why did this request behave that way" You need aggregates, not per-request forensics
Zipkin / Jaeger clients, OpenTracing / OpenCensusOSS Predecessors, merged into OTel Legacy — OpenTracing and OpenCensus are archived Only existing systems; do not start here
SDK-native tracing — Langfuse SDK, LangSmith SDK, MLflowmixed Alternative, most now OTel-compatible Fastest to adopt; check there is an OTel export path before committing Speed matters and the tool is already chosen
The question to ask a vendor: "can I export raw OTel spans to a backend of my choosing?" If yes, adopting them is reversible. If no, you are choosing a backend and an instrumentation layer at the same time — which is how observability becomes the thing you cannot migrate off.

3 · AI gateways landscape

This section is the short version. AI Gateway — The Control Point is the full page: the 14-capability checklist, an expanded OSS matrix, a proper side-by-side of the five cloud gateways, routing strategies, semantic caching, MCP gateways and failure modes.

An AI gateway is a reverse proxy that understands model traffic. It exists so that key management, routing, fallback, rate limiting, caching, cost attribution, guardrails and logging live in one place instead of being reimplemented in every application. If you have more than two applications calling models, you already need one.

Gateway Strengths Trade-off Choose when
Open source
LiteLLM ProxyOSS + SaaS 100+ providers behind one OpenAI-shaped API; virtual keys, budgets, fallbacks, cost tracking Python service to operate; a hop on the critical path Default for most teams — quickest route to multi-provider
Portkey GatewayOSS + SaaS Very fast edge gateway, routing, retries, caching, guardrails Richer features sit in the paid tier Latency-sensitive, want OSS with a hosted upgrade
Kong AI GatewayOSS + SaaS AI plugins on a mature API gateway — auth, quotas, transformations Kong concepts to learn if you are not already on it Kong is already your API layer

Apache APISIX, Higress, Traefik AI pluginsOSS AI routing on an existing ingress AI features are newer than the core proxy You want one proxy for all traffic
Gloo AI Gateway (Solo.io)OSS + SaaS Envoy-based, service-mesh adjacent, policy-rich Enterprise-shaped You run a mesh already
Bifrost, GPT Router, llm-gatewayOSS Lightweight, low-overhead routers Smaller feature sets and communities You want the thinnest possible hop
Managed & cloud-native

Default: if you are on a platform, use its gateway — Mosaic AI Gateway on Databricks, APIM on Azure. Otherwise LiteLLM Proxy to start, and move to Portkey or Envoy AI Gateway when latency or scale makes the hop expensive.

What the gateway takes off every application

The reason a gateway is the highest-leverage shared component: it applies to every application, in any language, with zero application code. Nine of the thirty-seven requirements in the blueprint can be satisfied here and nowhere else as cheaply.

Concern What you stop writing in every app
Model access & routingProvider SDKs, endpoint config, one API shape for every model
Fallback & retries"Primary down → secondary" logic, backoff, load balancing across deployments
Rate limits & quotaPer-key, per-user, per-team limits — including token-based, not only request-based
Budgets & cost capsSpend ceilings per team or project, alerts, hard stops
Cost attributionSpend tagged to team, project and use case without touching app code
Payload loggingRequest and response capture into your observability backend
CachingExact and semantic caching across all callers, not once per app
GuardrailsPII redaction and injection screening applied uniformly
Key managementVirtual keys per team — rotate centrally, never distribute provider keys

What "gateway config" actually looks like

LiteLLM, because it is the most likely default. Note that the applications never learn any of this exists — they keep calling claude-sonnet at the gateway URL.

# config.yaml
model_list:
  - model_name: claude-sonnet                 # the alias apps ask for
    litellm_params:
      model: anthropic/claude-sonnet-5
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: claude-sonnet                 # same alias again = load balanced
    litellm_params:
      model: bedrock/anthropic.claude-sonnet-5
      aws_region_name: eu-west-1

router_settings:
  routing_strategy: latency-based-routing
  fallbacks: [{ claude-sonnet: [claude-haiku] }]
  num_retries: 2
  allowed_fails: 3                            # circuit breaker
  cooldown_time: 30

litellm_settings:
  cache: true
  cache_params: { type: redis, ttl: 3600, supported_call_types: [acompletion] }
  callbacks: [langfuse, otel]                 # tracing + payload logging
  guardrails:
    - guardrail_name: pii
      litellm_params: { guardrail: presidio, mode: pre_call }
    - guardrail_name: injection
      litellm_params: { guardrail: lakera, mode: pre_call }

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  max_budget: 5000                            # org ceiling, USD per period
  budget_duration: 30d

Per-team virtual keys then carry their own limits and cost tags:

curl -X POST $GATEWAY/key/generate -H "Authorization: Bearer $MASTER_KEY" \
  -d '{"team_id":"ops-eai","models":["claude-sonnet"],
       "max_budget":400,"budget_duration":"30d",
       "tpm_limit":200000,"rpm_limit":500,
       "metadata":{"cost_centre":"EAI-1042","use_case":"incident-search"}}'
That single call is quota, budget and cost attribution for an entire team — and the application never knows it happened. This is the concrete reason the gateway belongs outside the application rather than inside a shared library: it governs code you do not control, in languages you did not choose.

Decide this before you adopt one: the gateway is on the critical path of every request. What happens when the gateway is down? Either a direct-to-provider fallback in the client, or an accepted outage with a stated SLO. "We will add HA later" quietly means the gateway is a single point of failure for every AI application at once — and you find out during the first incident.

The unfashionable answer is often right. The genuinely hard parts of orchestration are durability, resumption and versioning — not the graph DSL. Temporal or Step Functions plus plain Python solves those properly and has done for a decade. Reach for a graph framework when the topology itself is the complexity; reach for durable execution when surviving failure is the complexity. Most production systems have the second problem.

Before adopting any of this, ask: is the question actually multi-hop? GraphRAG and temporal graphs earn their cost on questions like "what depends on this service, transitively" or "what were the themes across ten thousand tickets". If your real question is "find me something similar", a hybrid vector + keyword search is cheaper, faster and easier to explain — and it is what most teams needed.

6 · Code structure graphs landscape

A knowledge graph of a codebase — files, symbols, calls, imports, inheritance, data flow. Distinct from document RAG, and increasingly the substrate that makes coding agents useful: it answers "what calls this?" and "what breaks if I change it?", which similarity search cannot.

Name collision worth knowing. Glean is Meta's open-source source-code indexing system. It has nothing to do with the enterprise search product of the same name. Say "Meta's Glean" or "Glean code indexing" in design discussions.

Picking one. Feeding an agent → Blarify, or tree-sitter into Kùzu/FalkorDB if you want your own schema. Impact and data-flow analysis → Joern. A Java estate → jQAssistant into Neo4j. Accurate navigation across many repos → SCIP. Just enough context for a coding agent and nothing more → a repo map, which needs no database at all.
Start with the repo map. A ranked tree-sitter symbol map solves most coding-agent context problems for a fraction of the effort. Build the graph when you actually need multi-hop answers — blast radius, transitive callers, dead code across module boundaries — because that is when the traversal earns the pipeline you now have to maintain.

7 · Token efficiency on large codebases practice

Working an AI coding assistant against a large repository is mostly a context problem, not a model problem. The levers below are ordered by impact, and the first four cost nothing.

# Lever Why it works Cost
1Delegate exploration to subagents A subagent burns its own context reading twenty files and returns a paragraph. Your main window receives the conclusion, not the dumps. "Find where retry logic lives across the services" should almost never run in the main session. Free
2Clear between unrelated tasks Compaction is lossy and costs tokens to perform; clearing is clean. Check where the window is actually going before optimising anything else — the answer is usually surprising. Free
3Keep the project memory file lean CLAUDE.md is prepended to every request. Point at files rather than inlining them. A 500-line memory file is a tax on every turn of every session. Free
4Prune MCP servers Every connected server's tool schemas sit in context on every request. Three chatty servers can cost more than the code you are reading. The most common silent bloat. Free
5Reference files explicitly @src/auth/session.py skips an entire search-and-read cycle versus "find the session handling code". Free
6Skills instead of a large memory file Skills load on demand; the memory file is always resident. Free
7Plan before executing Design first, then act — avoids exploratory thrash filling the window with dead ends. Free
8Structural search over text search ast-grep matches code shapes; far fewer false positives than grep, so fewer files opened. Install
9Symbol-level retrieval A language server returns one function, not one file. Setup
10A code knowledge graph Structural questions answered as nodes and edges instead of file text. Worth it once the repo is large, unfamiliar and the questions are genuinely structural. Setup + upkeep
Do 1–4 first. They are free, take an afternoon, need no maintenance, and in most codebases they deliver the bulk of the available saving. Tooling is the fourth step, not the first.

On the token-reduction numbers. Figures quoted around code-graph tooling — "49×", "71.5×" — are community-reported on particular workloads, not independent benchmarks, and they measure structural queries where a graph is inherently favourable. Expect a real but far smaller average across a normal working session, and measure it on your own repo before quoting it to anyone.
The staleness trap. A code graph must be rebuilt after significant changes. A stale graph is worse than none, because it is confidently wrong — and if a pre-tool hook makes the assistant consult it before searching, wrong answers arrive first. Wire the rebuild into a post-merge git hook or CI. Never rely on remembering to re-run it.
An ontology is not the answer to this problem. An ontology encodes business meaning — Study, Compound, Incident. A code graph encodes structural facts — this function calls that one. Tools like Graphify derive the second automatically from source. Nothing about making a coding assistant cheaper on your repository requires the first. See Ontology Builder for where ontologies genuinely earn their cost.
